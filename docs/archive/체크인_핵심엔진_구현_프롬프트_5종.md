## 프롬프트 2: 리스크 점수 엔진 구현

```
docs/BUSINESS_LOGIC.md의 "2. 리스크 점수 계산" 섹션을 읽어. 이게 정본이다.

### 구현할 것: 리스크 점수 계산 서비스

파일 위치: src/services/riskEngine.ts (또는 프로젝트 구조에 맞게)

#### 핵심 로직:

1. calculateRiskScore(projectId) 함수:

   Fp (법령 준수 점수) 계산:
   - law_checks 테이블에서 해당 프로젝트의 법령 체크 결과 조회
   - violated_count / applicable_count × 100
   - 각 법령의 risk_weight 적용 (가중 평균)

   Oc (공정 관리 점수) 계산:
   - projects 테이블에서 start_date, end_date, progress_rate 조회
   - expected_progress = (오늘 - 시작일) / (종료일 - 시작일) × 100
   - delay_ratio = max(0, expected_progress - actual_progress)
   - Oc = min(100, delay_ratio × 2)

   Ch (체크리스트 점수) 계산:
   - checklist_items 테이블에서 is_required=true인 항목 조회
   - unchecked / total × 100

   최종 점수:
   R = Fp × 0.45 + Oc × 0.25 + Ch × 0.30

   등급 판정:
   - 0~25: safe
   - 26~50: caution
   - 51~75: warning
   - 76~100: danger

2. risk_scores 테이블에 이력 저장 (매번 새 row INSERT)
3. projects.risk_score, projects.risk_grade에 최신값 UPDATE

#### API 엔드포인트:
docs/API_SPEC.md의 "5. 리스크 API" 참조.
- POST /api/projects/:id/risk/calculate — 수동 재계산
- GET /api/projects/:id/risk — 최신 점수
- GET /api/projects/:id/risk/history — 이력 (from/to 쿼리 파라미터)

#### 자동 트리거:
체크리스트 항목 체크 시, 법령 체크 결과 변경 시, 공정률 업데이트 시 자동으로 calculateRiskScore 호출.
해당 트리거 위치(체크리스트 PATCH API, 법령체크 POST API 등)에 호출 코드 삽입.

#### 테스트:
테스트 데이터로 계산 검증:
- 법령 12개 중 2개 위반, 공정 10% 지연, 체크리스트 70% 완료
- 예상: Fp = (2/12)×100 = 16.67, Oc = min(100, 10×2) = 20, Ch = 30
- R = 16.67×0.45 + 20×0.25 + 30×0.30 = 7.5 + 5.0 + 9.0 = 21.5 → safe

이 테스트 케이스가 통과하는지 확인해줘.
완료 후 docs/BUSINESS_LOGIC.md의 리스크 점수 섹션에 ✅ 표기.
```

## 프롬프트 3: 법령 룰 엔진 구현

```
docs/BUSINESS_LOGIC.md의 "3. 12개 법령 체크 로직"을 읽어. 이게 정본이다.

### 구현할 것: 법령 룰 엔진 서비스

파일 위치: src/services/lawEngine.ts (또는 프로젝트 구조에 맞게)

#### 핵심 로직:

1. checkAllLaws(projectId) 함수:
   - laws 테이블에서 12개 법령 전체 조회
   - 각 법령별로 checkSingleLaw(projectId, lawId) 실행
   - 결과를 law_checks 테이블에 저장

2. checkSingleLaw(projectId, lawId) 함수:
   각 법령의 check_conditions JSON을 읽고 조건별 판정:

   건설산업기본법 제28조:
   - warranties 테이블에 해당 프로젝트의 하자담보가 등록되어 있는지 확인
   - 없으면 → violated, 있으면 → compliant

   민법 제667조:
   - 프로젝트에 체크리스트가 존재하고 일부라도 완료되었는지
   - 체크리스트 0% → violated

   건산법 시행령 별표4:
   - warranties의 duration_years가 BUSINESS_LOGIC.md의 공종별 기간과 일치하는지
   - 기간 미달 → violated

   공정거래법:
   - 프로젝트 budget 대비 실제 지출 비율 (현재 데이터 없으면 not_applicable)

   민법 제580조:
   - photos 테이블에 자재 관련 사진이 있는지 (category로 판별)
   - 자재 사진 0개 → violated

   건설분쟁조정:
   - risk_score가 50 이상인 프로젝트에서 증거(is_evidence=true) 사진이 있는지
   - 증거 0개 → violated, risk 50 미만 → not_applicable

   소비자기본법:
   - 프로젝트 type이 residential(주거)이면 적용, 아니면 not_applicable
   - 적용 대상인데 체크리스트에 소비자 관련 항목 미완료 → violated

   전자서명법:
   - photos 중 sha256_hash가 null인 사진이 있는지
   - null인 사진 존재 → violated

   근로기준법:
   - 현재 데이터 없으면 pending (향후 근로자 관리 모듈에서 체크)

   산업안전법:
   - checklists에서 category가 'safety' 관련인 체크리스트 완료율
   - 안전 체크리스트 50% 미만 → violated

   건축법:
   - 프로젝트 status가 'completed'인데 관련 검사 체크리스트 미완료 → violated
   - 미완료 상태면 pending

   민사소송법:
   - photos 전체의 sha256_hash 존재 여부 + Merkle Tree 생성 여부
   - 해시 미생성 → violated

3. 각 법령 체크 결과를 law_checks 테이블에 INSERT/UPDATE
   - status: compliant/violated/not_applicable/pending
   - details: 판정 근거 JSON

4. 전체 법령 체크 후 → 리스크 점수 자동 재계산 트리거 (프롬프트 2의 calculateRiskScore 호출)

#### API 엔드포인트:
docs/API_SPEC.md의 "6. 법령 API" 참조.
- POST /api/projects/:id/law-check — 12개 법령 전체 체크 실행
- GET /api/projects/:id/law-checks — 체크 결과 목록
- GET /api/projects/:id/go-nogo — GO/NO-GO 판정 (아래 참조)

#### GO/NO-GO 판정:
docs/BUSINESS_LOGIC.md의 "1. GO/NO-GO 판정 알고리즘" 참조.
getGoNoGo(projectId) 함수:
- law_checks에 violated가 하나라도 있으면 → NOGO
- risk_score >= 76이면 → NOGO
- 필수 체크리스트 완료율 < 80%이면 → NOGO
- 그 외 → GO
- reasons 배열에 NOGO 사유 전부 담아서 반환

완료 후 docs/BUSINESS_LOGIC.md의 법령 체크 섹션에 ✅ 표기.
```

## 프롬프트 4: SHA-256 증거 무결성 시스템 구현

```
docs/BUSINESS_LOGIC.md와 docs/SCHEMA.md를 읽어.

### 구현할 것: SHA-256 해시 + Merkle Tree 증거 무결성 시스템

파일 위치: src/services/evidenceEngine.ts (또는 프로젝트 구조에 맞게)

#### 1. 사진 업로드 시 SHA-256 해시 자동 생성

사진 업로드 API (POST /api/projects/:id/photos)에 다음 로직 추가:

uploadPhoto(file, projectId, userId) 함수:
  a. 파일을 S3(또는 로컬 스토리지)에 저장
  b. 파일 바이너리 → SHA-256 해시 생성 (crypto 모듈 사용)
  c. 썸네일 생성 (sharp 라이브러리, 300px)
  d. EXIF 메타데이터 추출 (exif-reader 또는 sharp):
     - GPS 위도/경도
     - 촬영 일시
     - 디바이스 모델
     - 원본 해상도
  e. photos 테이블에 저장:
     - file_url, thumbnail_url, file_name, file_size, mime_type
     - sha256_hash: 생성한 해시값
     - uploaded_by: userId
  f. photo_metadata 테이블에 저장:
     - latitude, longitude, taken_at, device_model, original_width, original_height
  g. 해시 생성 성공 여부 응답에 포함

코드 예시 (Node.js):
```typescript
import crypto from 'crypto';

function generateSHA256(buffer: Buffer): string {
  return crypto.createHash('sha256').update(buffer).digest('hex');
}
```

#### 2. Merkle Tree 생성

프로젝트 내 전체 증거 사진의 무결성을 하나의 루트 해시로 보장.

generateMerkleRoot(projectId) 함수:
  a. photos 테이블에서 해당 프로젝트의 is_evidence=true인 사진 전체 조회
  b. 각 사진의 sha256_hash를 리프 노드로
  c. 쌍씩 합쳐서 SHA-256 → 부모 노드 생성
  d. 홀수개면 마지막 노드를 복제해서 쌍 맞춤
  e. 루트 해시까지 반복
  f. 루트 해시를 각 사진의 merkle_root에 UPDATE

코드 예시:
```typescript
function buildMerkleTree(hashes: string[]): string {
  if (hashes.length === 0) return '';
  if (hashes.length === 1) return hashes[0];

  const nextLevel: string[] = [];
  for (let i = 0; i < hashes.length; i += 2) {
    const left = hashes[i];
    const right = hashes[i + 1] || left; // 홀수면 복제
    const combined = crypto.createHash('sha256')
      .update(left + right)
      .digest('hex');
    nextLevel.push(combined);
  }
  return buildMerkleTree(nextLevel);
}
```

#### 3. 무결성 검증

verifyEvidence(photoId) 함수:
  a. photos 테이블에서 사진 조회
  b. S3에서 파일 다운로드
  c. 파일 바이너리 → SHA-256 재계산
  d. DB에 저장된 sha256_hash와 비교
  e. 일치하면 "무결성 확인", 불일치면 "변조 의심"

verifyMerkleTree(projectId) 함수:
  a. 전체 증거 사진의 해시로 Merkle Tree 재생성
  b. 저장된 merkle_root와 비교
  c. 결과 반환

#### API 엔드포인트:
- POST /api/projects/:id/photos — 기존 업로드 API에 해시 생성 로직 추가
- POST /api/projects/:id/evidence/merkle — Merkle Tree 생성/갱신
- GET /api/photos/:id/verify — 개별 사진 무결성 검증
- GET /api/projects/:id/evidence/verify — 전체 Merkle Tree 검증

#### 테스트:
1. 사진 업로드 후 sha256_hash가 64자 hex string인지 확인
2. 같은 파일 두 번 업로드하면 같은 해시 나오는지 확인
3. 다른 파일이면 다른 해시 나오는지 확인
4. Merkle Tree: 사진 3개 → 루트 해시 1개 생성되는지 확인
5. 파일 변조 시뮬레이션: DB 해시와 불일치 감지되는지 확인

완료 후 docs/BUSINESS_LOGIC.md 관련 섹션에 ✅ 표기.
```

- 프로젝트별 리스크 점수 카드 (점수 + 등급 컬러 + GO/NO-GO 배지)
- 긴급 이슈 알림 영역 (법령 위반, 하자담보 만료 임박)
- 리스크 점수 추이 차트 (recharts 활용, 최근 30일)

### 4. 프로젝트 상세 페이지 연결

/projects/:id 페이지에서:
- 리스크 점수 게이지 (0~100, 등급별 색상)
- 12개 법령 체크 결과 (준수 ✅ / 위반 ❌ / 미적용 ➖ / 대기 ⏳)
- GO/NO-GO 큰 배지 (GO: 초록, NOGO: 빨강 + 사유 목록)
- 증거 현황 (전체 사진 수, 해시 생성 완료 수, Merkle Tree 상태)
- 하자담보 현황 (공종별 잔여 기간)

### 5. 테스트 시나리오

테스트 프로젝트 1개를 만들고 다음 시나리오 실행:
1. 프로젝트 생성 (카페 인테리어, 5천만원, 3개월)
2. 체크리스트 자동 생성
3. 체크리스트 일부 체크 (70%) → 리스크 점수 자동 계산 확인
4. 사진 3장 업로드 → SHA-256 해시 생성 확인
5. 법령 체크 실행 → 12개 법령 결과 확인
6. GO/NO-GO 판정 확인
7. 대시보드에서 전체 데이터 표시 확인
